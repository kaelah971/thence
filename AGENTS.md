- Verify: `npm test` (live Neon TEST project, anchor-proven, ~8 min), `npm run typecheck`, `npm run lint`, `npm run build`. Never reset/truncate Neon.
- Focused suites: `npx vitest run tests/<file>.test.ts`. Live-handler tests dispatch the browser client to real route handlers (see `tests/f3-data.test.ts`, `tests/f32-requests-quotes.test.ts`); mock Satora via `setSatoraFetchersForTests` + `vi.spyOn(await getSatoraClient(), "getQuote")`.
- TEST DATABASE ISOLATION (F6.2.1, critical): live integration tests run ONLY with an explicit `THENCE_TEST_DATABASE_URL` pointing at the isolated test database (see `tests/test-db.ts`). A generic `DATABASE_URL` NEVER authorizes live tests. Never point `THENCE_TEST_DATABASE_URL` at production; the guard refuses same-target config. Never run `npm test` without the test URL configured — live suites skip safely and pure tests still run.
- PRODUCTION DATABASE SEPARATION (S0, critical): local `.env` `DATABASE_URL` targets the anchored non-production test project. The production connection string lives ONLY in `~/.thence/production.env` (outside the repo, never auto-loaded). `npm run dev|start|db:migrate|db:push|db:studio` run `scripts/assert-nonprod-db.ts` first and refuse any target that is not localhost or anchored (`__thence_test_anchor`), or that matches the production file (pooler-normalized). Vitest proves the test DB identity once (`tests/global-setup.ts`) and scrubs `DATABASE_URL` from workers without proof. Production pilot switch: `npx tsx scripts/pilot-switch.ts <cmd> --production [--yes]` only.
- P4/R2 EXPIRED_UNFUNDED (critical): `EXPIRED_UNFUNDED` has exactly TWO authorized writers, both owner-initiated and evidence-gated, both committing under the per-transfer lock with a terminal-once `transfer_transitions` audit row. (1) P4 `POST /api/transfers/:id/close-expired` → `src/lib/expiry-resolution.ts`: fresh provider identity + expiry, no EVM tx ids, no recorded movement/mismatch/EVM proof/NIM funding, pinned HTLC, finalized on-chain no-activity scan. It closes on the verified ABSENCE of NIM funding — no NIM funding recorded and no on-chain activity under those gates — and never asserts that a refund occurred, because it proves only non-payment. (2) R2 `POST /api/transfers/:id/close-nim-returned` → `src/lib/nim-return-resolution.ts`: only on an on-chain verified FULL NIM return (chain proof, never provider claims; the history is cross-checked with two RPC methods on the same configured node, which is not a second-node proof) — the bound HTLC's creation re-verified as in R1, a macro-final spend whose `value + fee` equals the whole locked amount to the owner's own basic account, the source hash attributed to no other transfer, plus the shared P4 provider gates (`assessProviderEvidence`: fresh identity, terminal `expired`, no EVM fund/claim tx, every invoice copy expired past the settle margin, pinned HTLC), the Polygon no-activity scan and the local evidence gates re-run under the lock (evidence older than 2 minutes refused). Neither path signs, broadcasts, claims or refunds anything, and R2 adds no schema or migration. The planner only reports `evidence-gated-close`; the server reconciler can never initiate either close and never applies an `EXPIRED_UNFUNDED` transition. Neither route proves a Lightning payout: P4 asserts only that no NIM funding is on record, R2 asserts only that a full NIM return was verified on-chain. Copy may describe R2's verified on-chain NIM return, but must never call either one a NIM refund or imply the Lightning payment succeeded. Production rollout of P4 requires migration 0015 (operator, explicit approval).
- P1 PAYMENT TRACKING: exactly one lifecycle driver per (owner, transfer) — `src/ui/lib/payment-tracker.ts` (shared, ref-counted, coalesced, abortable, backoff 3→30 s, 15 s cap pre-funding, 60 s after 429, paused while hidden and woken by visibility/focus/pageshow/online/`kickPaymentTracker`). Never add another polling loop; subscribe via `useSettlement().track`. The tracker never claims.
